# openframe-chocolatey-packages — Chocolatey feed source

What ends up in the GCS bucket `github-wif-xxxx-choco-feed` (see `openframe-saas-tf/openframe-saas/dev/shared/03-github-wif`, dev only for now) and how it is built.
The bucket holds a **static NuGet v3 feed** generated by [Sleet](https://github.com/emgarten/Sleet) from `.nupkg`
files mirrored from `community.chocolatey.org`. Agents read it directly at `https://choco.<env public domain>/index.json`:
an external HTTPS load balancer with a backend bucket, world-readable, no gateway in the path.

## How the PoC feed was built

1. `packages.yaml` lists the curated ids (`chocolatey` itself + 7 apps).
2. `scripts/sync-community.py`
   - asks the community **v2 OData API** for versions: `FindPackagesById()?id='<id>'&$orderby=Published desc`,
     keeps the newest `IsApproved=true`, `IsPrerelease=false` entry (the API's `IsLatestVersion` flag is unreliable, several versions carry it);
   - downloads the `.nupkg` from the entry's `content src` (redirects to `packages.chocolatey.org/<id>.<version>.nupkg`);
   - reads the `.nuspec` inside and **follows every declared dependency** (`[x]` = exact pin, `x` = minimum → newest), so the
     closure is complete: `7zip` → `7zip.install` → `chocolatey-core.extension` → `chocolatey-compatibility.extension`;
   - extracts vendor URLs and pinned checksums from `tools/chocolateyInstall.ps1`;
   - writes `downloads/*.nupkg` and `catalog.json` (sha256 of every file, community hash, published date, license, deps, vendor URLs).
   - 1 request/second, 4 retries on 429/503: one runner, low rate, no ToS issue.
3. `scripts/pack-own.py` builds our own packages from `packages/<id>/` (nuspec + `tools/`) into `downloads/` as plain OPC zips,
   since the Linux runner has no `choco pack`, and records them in `catalog.json` with reason `own`.
   First one: **`openframe-client`**, the agent bootstrap as a package (link-only, parameters carry tenant + enrollment).
4. `scripts/render-catalog.py` turns `catalog.json` into `docs/CATALOG.md` and classifies each package by what is inside the `.nupkg`.
5. Sleet (in the `mcr.microsoft.com/dotnet/sdk:8.0` container, `dotnet tool install -g sleet`):
   `sleet init` then `sleet push downloads/` into `feed/`, `sleet validate` → "Feed valid".
   `sleet.json` sets `baseURI` to the **public feed URL** (`https://choco.<env public domain>/`), the same host the LB serves.

Result for the 8 curated ids: **16 packages, 85 files, 171 MB**. Full list with provenance: [`docs/CATALOG.md`](docs/CATALOG.md).

## CI: `.github/workflows/publish.yml`

Daily (cron), on `workflow_dispatch`, and on pushes to `main` that touch `packages.yaml`, `packages/`, `overrides/` or `scripts/`.

| job | runner | what |
|---|---|---|
| `build` | ubuntu | `sync-community.py` → `pack-own.py` → `render-catalog.py` → Sleet builds `feed/` (baseURI = `vars.FEED_BASE_URI`) and `feed-test/` (baseURI = localhost) → artifacts |
| `test-install` | windows (choco preinstalled) | serves `feed-test/` on `localhost:8080`, asserts choco ≥ 2.0, `choco install` each id in `TEST_PACKAGES` from that source only, then uninstalls. This is the v3 + metapackage smoke test |
| `publish` | ubuntu, `main` only | `google-github-actions/auth` via WIF (no keys, no service account) → two `gsutil rsync` passes with per-class `Cache-Control` (CDN) → commits `catalog.json` + `docs/CATALOG.md` as the audit trail |

Repository **variables** (no secrets anywhere): `FEED_BASE_URI`, `FEED_BUCKET`, `GCP_WORKLOAD_IDENTITY_PROVIDER`; the last two are
outputs `github_workload_identity_provider` and `feed_bucket` of `openframe-saas-tf/openframe-saas/dev/shared/03-github-wif`, which binds `objectUser` on the bucket to this repository's `main` branch only.
`concurrency: feed` serialises publishes. The feed is rebuilt from scratch every run and `rsync -c` only uploads changed bytes.

Local equivalent of the build job (Sleet via Docker):

```
python3 scripts/sync-community.py && python3 scripts/pack-own.py && python3 scripts/render-catalog.py
docker run --rm -v "$PWD":/work -w /work mcr.microsoft.com/dotnet/sdk:8.0 bash -c \
  'dotnet tool install -g sleet >/dev/null; export PATH=$PATH:/root/.dotnet/tools; /work/scripts/build-feed.sh feed https://choco.<env public domain>/'
```

## Bucket layout (= `feed/`)

```
index.json                                  ← NuGet v3 service index; choco source URL is <baseURI>/index.json
sleet.settings.json, sleet.packageindex.json ← Sleet bookkeeping (needed for incremental pushes)
search/query                                ← static "list everything" search document (16 hits)
autocomplete/query
flatcontainer/<id>/index.json               ← versions list          e.g. {"versions":["155.0.8059.12"]}
flatcontainer/<id>/<ver>/<id>.<ver>.nupkg   ← the package itself     ← what choco downloads
flatcontainer/<id>/<ver>/<id>.nuspec
registration/<id>/index.json                ← metadata + dependency graph per package
registration/<id>/<ver>.json
```

Everything is lower-cased by Sleet (`GoogleChrome` → `googlechrome`), which is what the NuGet client expects.
The LB serves bucket object `<path>` at `https://choco.<domain>/<path>` one-to-one; no rewriting needed.

Publishing to the bucket (CI, WIF, no keys):

```
gsutil -m -h "Cache-Control:public, max-age=31536000, immutable" rsync -r -c -d -x '^(?!.*\.nupkg$).*' feed/ gs://github-wif-xxxx-choco-feed/
gsutil -m -h "Cache-Control:public, max-age=60"                  rsync -r -c -d -x '.*\.nupkg$'         feed/ gs://github-wif-xxxx-choco-feed/
```

Two passes because the LB runs Cloud CDN in `USE_ORIGIN_HEADERS` mode: `.nupkg` names carry the version, so they are cached
for a year as immutable; every JSON document changes on publish, so it is cached for a minute. `rsync -d` deletes objects
removed from the feed. The bucket keeps no versions or soft-deleted objects: the feed is rebuilt from scratch on every run,
so the next publish is the rollback.

## Findings that change earlier assumptions

1. **The community feed is not link-only.** Of 16 packages, 5 embed the installer inside the `.nupkg`:
   `7zip.install` 2.9 MB, `notepadplusplus.install` 13 MB, `git.install` 62 MB, `vlc.install` 87 MB, and `chocolatey` itself 5.4 MB
   (`choco.exe`). Community does this for FOSS whose license allows redistribution and for stability. Link-only are Chrome, Firefox,
   Adobe Reader and the KB packages, i.e. proprietary vendors. So the bucket will hold binaries for FOSS packages unless we strip
   them ourselves, and egress is not "negligible" for those: one `git` install pulls 62 MB from our bucket.
   Decision needed: (a) accept embedded FOSS binaries as-is (simplest, licenses permit it), or (b) re-package those to link-only
   in `overrides/` (more work, and installs then depend on the vendor URL).
2. **Metapackage pattern.** `7zip`, `git`, `vlc`, `notepadplusplus` are empty metapackages pinning `<id>.install`. The agent
   must install the metapackage id; choco resolves the pin. Dependency resolution therefore happens in choco, not in our backend.
3. **`chocolatey-core.extension` is required by almost everything** (min version `1.3.3`, we mirror `1.4.0`). It must be in
   the feed or every install fails.
4. **Checksum pins**: Chrome pins sha256 of `googlechromestandaloneenterprise64.msi`, an unversioned URL that Google overwrites
   on every release. The community package is re-published within a day; our sync must run at least daily or Chrome installs
   fail in between.
5. **`IsLatestVersion` in the v2 API is not trustworthy** (three Chrome versions carried it). Pick by `Published desc` + `IsApproved`.
